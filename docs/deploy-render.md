# Deploy Nimmari on Render + Turso (recommended)

This is the primary, recommended way to run Nimmari: Render runs the Docker image
(Chromium included for HTML-form rendering) and Turso hosts the database. Both have
free tiers, which are enough for personal use and evaluation.

> Free-tier facts below were checked on **14 October 2026** against the providers'
> official pages. Providers change their terms; re-check the linked pages.

## What the free tiers mean for Nimmari

**Render free web service** ([render.com/docs/free](https://render.com/docs/free))
- No card needed; 0.1 CPU / 512 MB RAM. PDF rendering with Chromium works but is slow; use a paid
  instance for regular use.
- **Spins down after 15 minutes without inbound traffic.** The next request wakes it
  up, which takes about one minute. A signer opening a link may see Render's loading page.
- **Ephemeral filesystem**: anything written to local disk (including a local SQLite
  file) is lost on redeploy, restart or spin-down. This is why the database lives in Turso.
- 750 free instance hours per workspace per month; outbound bandwidth and build
  minutes count against the workspace's monthly included amounts.
- Outbound SMTP ports 25/465/587 are blocked (use an HTTP email API such as Resend).
- Render may restart free services at any time and says free instances should not
  be used for production applications.

**Turso free plan** ([turso.tech/pricing](https://turso.tech/pricing))
- $0/month, no credit card: up to 100 databases, 5 GB storage, 500 million rows read
  and 10 million rows written per month, 1-day point-in-time restore.
- Signed PDFs are stored in the database, so storage is the limit that matters most.

## Performance on the free tier

Measured 7.10.2026 (Frankfurt, 0.1 CPU / 512 MB, Turso Ireland): signing an HTML document, including the Chromium PDF render, takes about 10 s (9.4–10.4 s). Upload, send and PDF fetch each take under 1.5 s. After about 15 minutes idle the service sleeps, and the first request took 27.6 s. The free plan is fine for evaluation. For regular use, pick the cheapest paid instance. Clients can pre-warm the service by calling `/api/health` when the UI opens. Details: [benchmarks/render-free-2026-10-07.md](benchmarks/render-free-2026-10-07.md).

For an agent-run installation using the prebuilt image and HTTP APIs (no provider CLIs or fork required), follow [INSTALL-FOR-AGENTS.md](../INSTALL-FOR-AGENTS.md). The steps below are the alternative manual Blueprint workflow.

## Steps

1. **Create the database** (Turso CLI: <https://docs.turso.tech/cli/introduction>)
   ```bash
   turso auth signup            # or: turso auth login
   turso db create nimmari
   turso db show nimmari --url        # -> DATABASE_URL (libsql://...)
   turso db tokens create nimmari     # -> DATABASE_AUTH_TOKEN
   ```
   The schema is created automatically: the container runs SQL migrations on start.

2. **Fork or copy the repository** to your GitHub account.

3. **Create the service from the Blueprint.** In the Render Dashboard choose
   *New → Blueprint*, select your repository; Render reads `render.yaml`.
   Fill in the prompted values:
   - `DATABASE_URL`, `DATABASE_AUTH_TOKEN` from step 1
   - `BETTER_AUTH_URL` and `APP_URL`: your service URL, e.g. `https://nimmari-xxxx.onrender.com` (Render shows it after the first deploy; redeploy after setting them). The blueprint also pins `region: frankfurt`; change it if you prefer another region.
     (you can set them after the first deploy when the URL is known, then redeploy)
   - optional `RESEND_*` and `NIMMARI_API_*` values; leave empty if unused.
   `BETTER_AUTH_SECRET` is generated by Render.

4. **Deploy and check health:** `https://<your-service>.onrender.com/api/health`
   should return `{"status":"ok"}`.

5. **Provision your account** using the root `NIMMARI_API_KEY` and [admin API bootstrap](../README.md#create-an-api-key-for-an-ai-agent), then log in at `/login`, upload a document and send a test link. Public signup is disabled.

6. **(Optional) Custom domain:** add it in the service's *Settings → Custom Domains*,
   then update `BETTER_AUTH_URL` and `APP_URL` to the new origin.

## Operations
- **Backups:** Turso's free plan keeps 1 day of point-in-time restore. Export regularly
  (`turso db shell nimmari .dump > backup.sql`) if documents matter to you.
- **Updates:** push or sync your fork; Render redeploys automatically. Migrations run on start.
- **You are the data controller** for documents and signer data in your instance.
